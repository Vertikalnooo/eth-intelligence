# Cloud-Native Trust Architecture v2 — proposed, NOT ACCEPTED
Date: 2026-11-27. Design only. Baseline PR39 HEAD 497f816ff4359a1f58764176c101ccaf347fdc67 (532/532 offline tests); production main 11d0a6040abbd1bc1ab5fd76bb205e8e8032b23b. No executable changes or cloud provisioning. Stage 2 OPEN, recommendation_eligible=false, Stage 3–5 LOCKED.
 
## 1. Decisions and constraints
Retain previous local UID/IPC research as regression evidence, NOT a cloud startup recipe. Render Free filesystem is ephemeral, has shared 750 instance hours/workspace/month and cold starts. No private inbound free service is assumed. Existing public Render API remains SAFE_BASELINE, no privileged bindings or DB credentials. Proposed separate Python broker service, separate secret scope, no shared disk/env group, no admin or deployment tokens. It is stateless across requests: no local authority, no auto-resume. Its eventual HTTPS ingress is publicly reachable and must not be described as private network; authenticate every command. No keepalive, cron, automatic retry, background polling, or paid upgrade.
Cloudflare: one public HTTPS Owner Gateway on a stable exact workers.dev origin TBD before enrollment (not preview); separate private Owner Trust and Witness Workers, each with own SQLite Durable Object namespace and secret scope, accessed only via narrowly scoped Service Bindings. Existing deployed Witness stays DISABLED; a new version or namespace is a separate approval, no reuse/reset by this proposal. Gateway cannot directly access DO storage, signing keys, SQL credentials or provider control plane. Trust and Witness must not have a general signing endpoint. Bindings are scoped capabilities, not equivalent to OS UIDs, and the shared account administrator remains trusted. No trust in arbitrary RPC method parameters or incoming headers.
Neon Free: existing PostgreSQL 17, 0.25 CU, 1 GiB limit, 6-hour restore window. Use separate NOLOGIN schema owner and tightly scoped LOGIN users for broker operations only after separate approval; no inherited neon_superuser or role creation, bypass RLS, DDL, temp schema privilege or membership escalation. Existing ei2 functions accept role + state only, so new isolated schema ei3 proposed; never expose legacy functions to runtime roles. No schema change now. pgcrypto HMAC support is a design dependency to be verified using actual PG17 disposable fixture then separately authorized catalog read on Neon. Do not assume asymmetric signature verification extensions or invent crypto in PL/pgSQL. 
No live exchange transport in architecture v2 implementation; only synthetic loopback fixtures. Even valid SQL capabilities cannot restrict arbitrary code with Internet access on broker. Future live executor needs enforceable egress/request-count boundary and separate explicit review; absence on Free remains NO-GO for hostile broker threat. No claims of absolute distributed exactly-once delivery.

## 2. Trust boundaries and keys
| Component | Can hold | Must never hold |
|---|---|---|
| Owner iPhone | Passkey private key via authenticator, independently retained signed evidence/head set | SQL, Cloudflare deployment or attestation keys |
| Gateway | RP/origin configuration, public verification keys, fixed broker origin, scoped internal bindings | SQL creds, HMAC attestation keys, DO direct storage, owner private keys |
| Owner Trust | pinned credential public keys, challenge/use history, K_T (32 random bytes per epoch), optional independent receipt signing key | K_W, broker SQL passwords, owner private keys |
| Witness | independently pinned credential/public owner evidence, checkpoint/receipt history, K_W (32 random bytes per epoch), separate read-only audit key | K_T, SQL passwords |
| Broker | per-role SQL login passwords, public verifier pins, short-lived exact capabilities | K_T, K_W, owner signing keys, admin/migration/backup keys |
| PostgreSQL | K_T and K_W in protected NOLOGIN-owned private table, epoch/key metadata, immutable-by-runtime used IDs/ledger | owner private keys, provider API tokens |
| Existing public API | no privileged secrets; safe status only | all authority |
K_T/K_W unique per environment and ledger, not interchangeable with transport HMAC or audit keys. PostgreSQL HMAC-SHA256 attestation verification is symmetric, not direct verification of WebAuthn ECDSA or public-key signature. The owner signs standard WebAuthn assertions; Trust and Witness separately verify the actual assertion, exact challenge/action binding and their pinned public keys before issuing different MACs. PostgreSQL verifies BOTH MACs without trusting broker's decision. A single compromised signer cannot mint the other MAC. PG admin/DB compromise can read both keys; that risk is outside this guarantee. Key installation/rotation/revocation separately approved, never startup, secrets passed only through approved secret stores, not Git, URLs, logs, SQL literals in migration, CI artifacts, or dashboard screenshots. No generic signing or raw key export. Secure provisioning channel and account permissions acceptance required. 
For terminal SUCCESS/UNKNOWN (internal only, not additional owner ceremony), both services must bind to already consumed authorization and exact terminal evidence. UNKNOWN always freezes. SUCCESS cannot be assumed truthful from broker-supplied snapshot: require independently verifiable execution receipt and read-only SQL evidence; actual executor provenance is an unresolved gate. Offline synthetic signed fixture only.

## 3. Wire contract (normative proposal, not implemented)
Protocol EI-CAP-3. Fixed ASCII canonical frame: version, environment, ledger ID, Witness object ID, candidate SHA, key_epoch, op, authorization ID, plan ID, grant ID, epoch, old checkpoint, new checkpoint, owner journal head, credential revision, trust sequence, witness sequence, evidence digest, scope, issued_at, not_before, expires_at. Each field has fixed type/length, lower hex IDs, canonical unsigned decimal safe range for integers, exact enumerated op/scope, no escaping/whitespace/duplicates/unknown fields; explicit length-prefixed fields in fixed order, bounded <=4096 bytes, shared byte-level vectors across JS/Python/SQL. Domain separation for trust MAC / witness MAC / challenge / receipt. Both MACs over identical canonical bytes with distinct domain prefix. Never reserialize arbitrary caller JSON as authoritative bytes. SQL must rebuild the canonical frame from strict fields and compare exactly. Unique 128-bit random authorization ID; one op per ID. Candidate and environment pin mandatory. Clock tolerance proposed <=5s; capability max lifetime 30s, grant <=120s, 900s cooldown retained; trusted server DB clock authoritative for SQL after lock acquisition. No TTL refresh, no fallback. Prewarm broker/DB with explicit harmless readiness before issuing short-lived authorization, never by background traffic; cold start misses deadline => freeze, no retry.
Owner challenge = SHA256(domain || canonical plan/action || fresh random nonce || prior owner-pinned heads); 32-byte nonce CSPRNG, stored before issuing challenge, exact RP/origin, user gesture and UV required, purpose binding. Independent Trust/Witness persist same challenge digest and expected heads BEFORE browser receives options; no capability on partial commit. Verify assertion independently against state and pinned key; atomic burn challenge on attempted verification (including malformed assertions, no rollback restoring unused state), final issue with version/CAS and durable revision. Storage sync/ack before releasing capability. Each verifier records approved body, evidence hash, one-use approval and sequence; disagreement or unknown acknowledgement freezes. No auto adoption of returned heads.
Transport: fixed Gateway->Broker HTTPS origin, no redirects, no caller URLs, capped JSON and timeout, authenticated body with complete dual capability and broker audience, per-request nonce; no bearer-only authorization for mutation. Signed receipt chain plus authenticated read-only snapshots, independent audit key; no sensitive response to unauthenticated requests. Broker reads only approved operation-specific function using parameters, no arbitrary SQL endpoint. Broker can be killed on timeout; provider may still commit. No retry of uncertain operation. No automatic reset, alarm, retry or queue redelivery. Shared per-step budgets fit remaining capability TTL; proposed 8s local SQL deadline and <=30s per authorization; no distributed cancellation guarantee.

## 4. PostgreSQL enforcement (not implementation)
New ei3 private schema/table for epoch, authorized candidate, external heads, sequence, dual verification keys, state, grants, spent authorization IDs and checkpoint history. Keys separate from audit views, runtime cannot SELECT, change, dump or access through functions. Install extension in trusted schema only, fixed search_path pg_catalog, trusted schemas, pg_temp last; all names qualified, no dynamic SQL; revoke default PUBLIC EXECUTE in same transaction as create, no public CREATE/TEMP or inherited legacy privileges. Dedicated NOLOGIN owner, role-specific wrapper EXECUTE only. No SECURITY DEFINER function exposes MAC oracle, reset, raw key reads or free-form transitions. 
Each wrapper: verify session identity/role and fixed operation; strict sizes/types/epoch/audience/plan; reconstruct bytes; check both pgcrypto.hmac values using reviewed constant-time comparison method (fixed length, no early exit; benchmark leakage; do not claim verified constant time before testing); lock singleton FOR UPDATE; recheck state, current external head/sequence, candidate/key epoch, DB time and expiry; consume unique authorization ID + old checkpoint; apply legal transition and append event in same transaction; COMMIT acknowledgement only. Invalid auth => no mutation; unknown result => client freeze even if transaction committed. Verify spent ID/event even after broker restart. Concurrency, rollback, SQL privilege escape, function/search_path and timing tests mandatory. Legacy ei2 stays untouched until separately authorized migration; runtime login cannot access old role functions. A PG restore can revert used IDs; external Witness/Trust and owner pins block new issuance, but a pre-existing unexpired stolen capability could still be replayed directly into restored PG until expiry. Recovery must disable/revoke old runtime credentials and network access as feasible, wait out maximum TTL + skew, rotate key epoch and reconcile before any re-enable; automatic rollback resistance of DB alone is NOT claimed. If cannot enforce restore fence, no production.
 
## 5. Cycle and recovery
Initial state absent/DISABLED => reject. No startup DDL, auto-genesis or credential installation. Separate owner approval gates for enrollment, ledger bootstrap, activation.
For each cycle:
1. Owner independently supplies last pinned tuple (identity, trust/witness heads, credential revision, PG checkpoint, candidate/key epoch); both verifiers require current match; no self-pinning. Save intent/pins externally before action. 
2. ARM: independently verified owner assertion and signed evidence; Witness durably claims checkpoint before any SQL ARM; Trust/Witness issue dual exact capability; PG consumes it atomically.
3. ISSUE: fresh owner challenge, both attest, PG creates one grant <=120s.
4. CONSUME: fresh owner challenge, both attest, PG durably consumes grant before synthetic fetch. No live data, no order path. No duplicate fetch on restart or uncertain acknowledgement.
5. Terminal SUCCESS/UNKNOWN scoped to exact consumed grant and independently verified receipt, UNKNOWN freeze. Audit read-only roles fetch real state/grant/event evidence, not caller-provided snapshots.
6. ADVANCE only after fresh owner WebAuthn bound to terminal digest, both compare ledger and prior claim; Witness advances once, Trust records receipt. Cache remains blocked until separate owner-confirmed receipt binds actual result and externally pinned latest heads. Cache only within original receipt age, never resurrect after restart. Public API remains deny-only. 
State machine: DISABLED/UNINITIALIZED -> (separate approval) READY -> CLAIMED -> ARMED -> ISSUED -> CONSUMED/PENDING -> CLOSED -> ADVANCED -> OWNER_CONFIRMED; any missing, expired, divergent, ambiguous transition => FROZEN. No reverse transitions in runtime. Partial commits are expected; no distributed atomic transaction. Recovery read-only classification from authenticated fresh nonce-bound snapshots of independent Trust/Witness/PG plus owner-held heads, exact role/candidate/epoch/evidence matching, repeat reads for races. FROZEN or MANUAL_REVIEW_ONLY only; no reset, repair, rollback or grants from audit. Unknown outcomes preserved even if service restarts. Operator restore/rekey requires separate explicit signed approval, old credentials revoked, TTL drain, new lineage, never silently adopt a restored head. 
Cloudflare PITR and Neon restore are not immutable evidence. Same-account Cloudflare rollback/compromise may affect BOTH verifiers. Owner-held receipt export outside both providers is required; compare exact latest intent AND receipt, not just last successful checkpoint. Independent owner signature mechanism for external journal remains a blocker: WebAuthn signs authenticator data/challenge, not arbitrary journal bytes. Proposed replace raw signing with domain-bound WebAuthn proof plus public-verifiable signed receipts retained manually in Files/locked note (no private key there); independent offline verification and custody on iPhone must be demonstrated, or retain existing separate signer with secure custody. Neither a note alone nor same-origin WebCrypto storage constitutes independent signing authority. Missing proof freezes; no assurance against combined provider/owner rollback.

## 6. iPhone enrollment (future, not executed)
Fix actual exact stable HTTPS Gateway origin/RP ID before any registration; do not use current onrender.com or preview alias by default, no wildcard/suffix matching. Verify origin ownership and isolation, no third-party JS, strict CSP, no embedding, same-origin CSRF/origin checks and no-cache. One explicit authorized enrollment ticket with hashed 256-bit random secret, short expiry, single atomic consumption, delivered privately out of band (no URL query, logs or chat). No enrollment route enabled in runtime baseline. Both private verifiers pin same credential ID/public COSE ES256 key, RP, user handle and initial count independently from verified registration proof; owner independently saves fingerprint and signed initial evidence before activation. Registration userVerification required, residentKey required; validate clientData type/challenge/origin/crossOrigin, RP hash, UP/UV, credential ID, algorithm/curve, authenticator flags and signCount; use pinned reviewed WebAuthn libraries, negative vectors. For assertions, verify userHandle, origin, challenge binding, signature, UP/UV, backup eligibility/state policy, count (nonzero monotonic; zero may be legitimate synced passkey; durable revision still increments), expiry and one-use. Actual Safari Face ID or device passcode flow, no claim of hardware uniqueness: iCloud sync supported. No password or SMS fallback, no automatic re-enrollment. Lost device = freeze, separately approved out-of-band recovery and key/credential rotation; recovery must not inherit old authority. Trust/UI compromise can misrepresent human intent: cannot prove human read a malicious screen. Independently retained intent display/receipt verification needed. No real iPhone test now.

Reject wrong hostname/CA/channel binding, timeouts; no connection strings in logs.
